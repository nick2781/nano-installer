The visual builder builds setups without the command line, on Windows 10 or later. It is a front end to
the CLI and shares the CLI's build engine, so it never spawns the CLI as a child process. Take
`nano-installer-gui-x64.exe` and the three runtimes from the
[latest release](https://github.com/nick2781/nano-installer/releases/latest), put them in one folder,
then start it:

```powershell
.\nano-installer-gui-x64.exe
```

It opens with an empty workspace and loads no example project. If you build the tool from source, the
same executable lands in `target/release/`, which is the path a contributor takes.

## A build in five steps

<Steps>

1. **Open project** and pick the folder holding `installer_config.json`.
2. **Refresh** re-reads the JSON, the XML, the assets and the payload. It never overwrites an output
   path you changed in this project.
3. **Parameters** sets the project folder, the output exe and an optional runtime directory. This is
   also where you decide whether the build produces a package for an estate: if it does, fill in the
   `.msi` that wraps the setup. **Reset output** restores `dist/<output.installer_name>`, and
   **Use automatic stub search** restores automatic lookup. The package path follows the setup's name
   until you type one of your own, and the preview line below shows the `--msi` the build receives.
4. **Build setup** builds asynchronously and re-validates the project in a worker thread, so the
   summary on screen cannot affect the result.
5. **Save log...** exports the full log, and **Open output** reveals the setup in Explorer. The
   **After build** option decides whether the output is revealed automatically.

</Steps>

<Aside type="note" title="Retry repeats the build with exactly the same parameters">

If a build fails, fix the file or the runtime it named, then press **Retry**.

</Aside>

## What the window shows

The window follows a traditional build workbench layout. A standard menu bar sits at the top, and the
project summary occupies the left. The main area shows the build log or the parameter page, and the
bottom holds the build action and a status bar that is always visible.

The left sidebar groups settings by purpose: configuration checks, version and setup language,
packaging inputs, installation settings. Packaging inputs cover the payload, the matching runtime, the
installer and uninstaller icons, and the uninstaller name. Installation settings cover whether the
setup asks for administrator rights and which directory it installs into by default.

When a path is too long for its box, it shows only the drive and the last segment; hover to see the
full path.

**Build warnings** lists what the last inspection found: a 1x/2x PNG with no counterpart, a locale that
is missing page text the default locale defines, and a language listed in `supported_locales` with no
file behind it.

<Aside type="caution" title="The inspection answers for one moment only">

"Last check passed" carries the check time and reflects the project state at that moment only, so
refresh after you change files on disk. **Build warnings** is a quick check of your assets, not a
replacement for the release checklist.

</Aside>

## Reading the log

The log lists the steps your build actually ran: the resolved paths and sizes of the installer and
uninstaller runtimes, the uninstaller's name in the bundle, the file count and size of each resource
directory, and the payload format. Then comes the bundle index, with a SHA-256 beside every entry.
Resources go straight into the custom bundle, so no intermediate `skins.zip` appears, and the payload
keeps the ZIP or 7z format you provided.

The uninstaller has its own UI bundle, and that bundle carries no payload. The log therefore collects
`layouts`, `assets`, `locales` and `scripts` once, tagging those lines with `Uninstaller bundle:`, then again
for the main setup. The payload goes in once, into the main setup.

If your project defines a `finalize.uninstaller` or `finalize.installer` command, the log shows that
step too: a `Running finalize.uninstaller: ...` line names the file and the command, and every line the
command printed follows. When the command fails, the log gives its exit code and leaves no setup
behind.

Log lines carry local timestamps in `[YYYY-MM-DD HH:mm:ss.SSS]` form, and everything in the log window
is selectable: you can drag with the mouse, scroll with the wheel and scroll sideways, and `Ctrl+A` and
`Ctrl+C` work. Warnings appear in amber and errors in red. **Copy all** copies the whole log with no
selection, and saved or copied text keeps the original wording and timestamps.

Menus keep a fixed minimum width and single-line labels, so they never move when you switch between
English and Chinese. **Open config** opens `installer_config.json` in your default editor, and the menu
also has clear log and exit. While a build runs, the buttons stay disabled, so you cannot start two
packaging tasks at once.

## Interface language

**View > Interface language** switches between English and Simplified Chinese, but it translates the
builder's own controls only. The language of the installers you produce comes from the project's
`locales` files and XML.

Build log wording stays in English no matter which interface language you pick, and errors from Windows
or the file system keep their original text, so you can still read the paths and error codes.

## What it does not do

The builder changes build parameters for the current build only and never rewrites your JSON or XML, so
your project configuration stays the single source of truth. A payload's compression follows its file
signature, which is why there is deliberately no compression dropdown: it would have no effect.
