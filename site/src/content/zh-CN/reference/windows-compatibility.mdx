发布出去的每个文件都只针对 `x86_64-win7-windows-msvc` 这一套目标构建，最低支持 Windows 7 SP1 x64。
也就是说，没有 32 位版本，也没有 ANSI 版本要另外维护。

可视化构建器 `nano-installer-gui-x64.exe` 用的是 eframe/egui，所以要 Windows 10 x64 及以上。不过它只负责
生成安装包，产出的安装包仍然按上面那个最低版本构建。

最低支持的版本已经在真机上验证过。这次验证用的是一台内部版本 7601 的虚拟机，装的是当前构建器生成的
安装包。每次构建也都会检查导入表，确认没用到新系统才有的 API；而虚拟机上的那次运行说明这些调用真能跑。
覆盖了哪些、没覆盖哪些，记在[当前生产状态](/zh-CN/project/status/)；想自己再跑一遍，见
[怎么跑这次验收](#怎么跑这次验收)。

## 运行时依赖什么

- Win32 Unicode API：窗口、控件和文字都走这一套。
- WIC 解 PNG，GDI 把解出来的图做透明混合。
- 注册表、shell 和进程接口，Windows 7 SP1 上都有。读注册表键的 32/64 位视图分别用
  `KEY_WOW64_32KEY` 和 `KEY_WOW64_64KEY`。命令输出要先按系统的 ANSI 代码页解开，再交给
  `MultiByteToWideChar` 转回来。这两个从 Windows XP 起就有。
- 服务控制管理器：脚本装的服务就是系统里的一条普通服务，所以装、改、停、删都走这套接口。本项目支持的
  系统都在 Windows 7 之前很久就带上了它。
- IMM32：输入法的组合窗和候选窗都归它管，Windows 7 自带。
- WinHTTP：按工程要求下载依赖，走 https 时开 TLS 1.1/1.2。

<Aside type="caution" title="Windows 7 SP1 上 TLS 1.2 要装补丁">
在 Windows 7 SP1 上，TLS 1.2 还得靠系统自己的 schannel 支持，也就是要装 KB3140245 或更新的补丁。
没装就直接报错，不会退回明文。
</Aside>

正式构建用固定的 `nightly-2026-02-25` 工具链，配 `rust-src`、`-Z build-std=std,panic_abort`、
静态链接的 CRT 和 `panic=abort`。

## 兼容性如何检查

每次构建都会检查 PE 导入表，范围是构建器、三个运行时和每一个生成的安装包。只要出现 Windows 8 或
Windows 10 才有的 API，构建就失败，所以这些文件在静态导入层面不依赖新系统。

静态检查证明不了安装包真能用，所以项目还补了一次实机验证。在内部版本 7601 上，PNG 解码、文字渲染、
鼠标输入、窗口行为、解压、安装和卸载都走通了，窗口拖动、最小化与还原，以及「卸载之后安装目录整棵消失」
也在其中。
逐条结果见[当前生产状态](/zh-CN/project/status/)。

<Aside type="caution" title="那次运行没覆盖的部分">
QEMU 这次已经覆盖窗口的最小化与还原，也用独立探针确认了光标形状；仍未覆盖多显示器缩放和服务的安装、
卸载。读屏只读到了无障碍信息，内容与 Windows 11 一致。NVDA 2023.3 虽然能装在这台 Windows 7 SP1 机器上，
每次真正启动却会让它终止。虚拟机上没有音频设备，所以第 8 项要另找一台有声卡的机器，或者由人坐在旁边听。
</Aside>

<Aside type="note" title="目标机器要装的补丁">
目标机器建议装 KB3033929（SHA-2 代码签名支持）；工程要下载依赖时，还得有 KB3140245 及之后的补丁。
</Aside>

## 怎么跑这次验收

上面几节说的是要求，这一节说的是怎么满足它——目的是留下能查的记录，而不是一段回忆。

**准备。** 找一台干净的 Windows 7 SP1 x64，内部版本 7601，装好 KB3033929。跑一遍会往机器上装东西，
所以先做快照。工程要下载依赖时，这台机器还得有 KB3140245 及之后的补丁，否则 TLS 1.2 用不了，这一条
记为「未覆盖」。构建不需要工具链：从发布里取构建器和那三个运行时（见[快速开始](/zh-CN/quick-start/)），
放进同一个目录，对着工程跑：

```powershell
.\nano-installer-native-x64.exe build --project <你的工程>
```

生成的 exe 拷到 Windows 7 机器上。用来验证的工程最好页面齐全、语言不止一种、带 PNG 图片、带应用文件，
还会建快捷方式、走卸载流程。`examples/TapTap` 再加上一份你自己的应用文件，就是这套文档一直用来验证的
样子。

**逐项观察。** 下面每一条都对应本仓库的一句承诺：

1. 用普通用户运行。窗口应当没有标题栏、四角是圆的，背景图和 logo 都画得出来（PNG 解码、透明混合、GDI
   绘制）。文字是工程自己的语言，鼠标移到能点的控件上会变成手型。
2. 按住背景拖动窗口，最小化，再还原。
3. 工程有多种语言时切换一次，页面应当重画。
4. 把每一页走一遍，包括会报出当前步骤的进度页；完成页配了启动程序的话，也点一下。
5. 装完看看机器上留下了什么：文件、快捷方式（桌面、开始菜单、开机启动）、卸载入口，以及卸载程序之后
   要读的清单文件。
6. 工程有 `scripts/install.rhai` 的话，核对一下脚本做了什么。
7. 从卸载入口卸载：产品的文件和快捷方式应当消失；没勾选删除时用户数据保留；安装目录空了就删掉。
8. 开着读屏软件（讲述人或 NVDA），让它念出当前页面、焦点，以及正在输入的字段。
9. 工程装服务的话，确认服务在、能启动，卸载后没有了。

**记录结果。** 记下系统版本（`winver` 显示「版本 6.1（内部版本 7601: Service Pack 1）」）、安装包的版本
或 tag、由哪个工程构建，以及是不是以管理员运行。再记下上面每一条的结果：实际发生了什么，或者哪一条
未覆盖、为什么。然后回仓库：

- 把看到的写进 `site/src/content/{docs,zh-CN}/project/status.mdx` 的「已验证」清单，并写明这次覆盖的是哪个 release；
- 在 `CHANGELOG.md` 的标记之下加一条 `已验证`，写明系统版本、覆盖的是哪个 release，以及未覆盖什么。

不必每个 release 都重跑。运行时、某一类页面、清单文件、卸载程序或某个 Win32 调用有变化时再跑。记录里
要写明覆盖的是哪个 release。它也不代表所有 Windows 7：32 位 Windows 7 和 ARM64 完全不支持，没装
SP1 的机器也不在范围内。
