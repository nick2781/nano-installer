## 从一个项目目录到单个可执行文件

```text
MyApp/
  installer_config.json + layouts/ + assets/ + locales/ + scripts/ + payload/
                                    |
                                    v
                     nano-installer-native-x64.exe
                                    |
                        按 payload 文件头选择运行时
                            /                       \
                lzma-stub-native.exe        zlib-stub-native.exe
                            \                       /
                            + bundle + 卸载程序
                                    |
                                    v
                             MyApp_Setup.exe
```

构建器和运行时是两个独立的程序，运行时就是安装包里真正干活的那个程序。所以生成的安装包里
只有运行时和你的项目数据，永远没有构建器。

你把应用文件交给构建器，它会看头几个字节来选运行时：`7z` 签名走 LZMA 运行时，`PK` 签名走 ZIP
运行时，选定之后把对应的那个复制出来。接着写入你配置的图标、版本信息和应用程序清单，再追加一份
bundle，里面装着 layouts、assets、locales、scripts 与应用文件，最后放上自包含的卸载程序。应用
文件保持你给的压缩格式，打包时不会再压一层。

两个成品都写完之后，构建器把它们交给工程自己的命令。卸载程序趁它还是独立文件时跑一次，这时它
还没被嵌进去；安装包则在全部写完、文件关掉之后跑一次。命令写下的每一行都进构建日志，返回非零就
中止构建，那份被拒的安装包也不会留在磁盘上。这两个钩子通常用来签名，也就是 NSIS 的 `!finalize`
与 `!uninstfinalize`；构建器自己不签名，配法见
[配置参考](/zh-CN/CONFIG_REFERENCE/#构建完成后的命令)。

## 生成的安装包内部

**启动。** 运行时靠 bundle 尾部的一份索引找到每个条目，条目旁边记着构建时算出的 SHA-256。所以
启动时不用把应用文件载入内存，读出来的字节也一定是当时写进去的那些，真正开始解压时才按偏移读取。
读取时逐段核对摘要，对不上就按条目名报错，把写了一半的那份删掉。

**界面。** 页面取自 `wizard.pages`（安装）和 `wizard.uninstall_pages`（卸载），每个页面都用 Win32
绘制：PNG 交给 WIC 解码，透明通道用 GDI alpha blend 合成。目前它支持绝对定位的位图与文字层，也支
持可嵌套的 `VBox`/`HBox`/`Content` 流式布局，内边距、外边距、百分比尺寸和 `flex-wrap` 折行都算在
内。控件有进度条、复选框与可展开面板的交互、可点击链接、目录选择框，还有就地文本编辑，带选区、剪
贴板和撤销栈；语言可以在运行时切换。窗口没有边框、四角是圆的，带任务栏图标，用双缓冲绘制，可以拖
动、最小化和关闭。页面用 `action="next"` 与 `action="back"` 前后走。项目里放了
`scripts/pages.rhai` 时，每次点 `next` 先问它的 `next_page(from)` 去哪一页，钩子拿到的只有只读原
语；`back` 则按用户来时的路退回来。

**读屏。** 运行时自己把每个控件画成像素，窗口里没有子窗口供客户程序遍历，所以窗口自己回答 Windows
问的那句「你在显示什么」。收到 `WM_GETOBJECT` 时，它用 `LresultFromObject` 交出一个 `IAccessible`，
由 COM 封送到客户程序所在的进程里去。报出去的是当前这一页的控件，顺序与页面布局记录的一致，包括角
色、名字、取值、状态与屏幕坐标。名字就是页面布局写下的文字，输入框取它上方的标签，下拉框取它当前
显示的那一行。客户程序请求执行默认动作时，走的就是用户点一下的那条路；焦点移动、取值与清单变化、
翻页，都由窗口主动发通知。对话框打开时，整棵树换成卡片上的两个答案，窗口的名字换成那句提问。
**任务正在跑的时候**没有控件可点，剩下的就是任务自己报的那句话和一根进度条，这两样按「被描述的对
象」一起报出去，进度条的取值是它画着的百分比。每变一次都由窗口主动播报：状态文字按活动区域播报，
进度条报成取值变化，两样都只在真的变了才报一次。输入框的取值不满足规则时，那句提示也走同一份描述：
它既是这个字段自己的描述，也在出现或换一条规则时按活动区域播报。向导打开的**那一帧只记不报**，因
为它是阅读器主动来读时看到的内容，而用户可以在第一帧画出来之前就开始打字，所以基准值是建窗口时记
下的，不是第一次重画时记下的。实现都在 `crates/nano-installer-core/src/accessibility.rs`；这份描
述每次调用都从运行时的共享状态现算，所以没有第二张需要与页面对齐的表。

**提问与提示。** 凡是用户必须回答的问题，比如退出确认，以及必须确认知悉的提示，运行时都画在窗口
内部，用的是 `ui.dialog_layout` 指定的那份布局，不交给系统弹窗。对话框就是一份普通布局，
`value-source="dialog:*"` 让它显示这次提问的正文和按钮文案；打开期间只有对话框上的控件响应点击，
`Enter`/`Escape` 分别对应确认和取消。脚本的 `show_message`、`show_error`、`ask_yes_no` 也画在
这张卡片上，被点中的那个按钮就是交还给脚本的答案。窗口按所在显示器的工作区居中，布局比桌面还大时
夹取到工作区内。

**任务。** 安装和卸载都在工作线程上跑，进度与页面切换靠一份共享状态发布出去，UI 线程收到刷新消息
后才重绘。绘制始终留在持有窗口的那个线程上，所以解压期间窗口照样能响应。

**安装。** 运行时先把文件暂存，然后写入清单文件和卸载注册表项，再创建你配置的快捷方式与自启动项。
卸载注册表项就是 Windows「程序和功能」里显示的那一条。它记着 Windows 安装列表要读的整组字段：产品
名、版本、发布者、安装目录、卸载命令与图标、静默卸载命令，以及按磁盘字节数算出的容量。它另外带两
个标记，声明这里没有单独的修改与修复步骤。目标目录里已有同一项目时按升级处理：被替换的文件记入回
滚日志，新应用文件里不再包含的文件会删掉，失败则恢复到先前版本。

**更新包。** 发布也可以做成更新包，而不做成完整安装包。`--delta-from` 点名它要替代的那一版的应用
文件包归档，构建器用运行时分别展开两份归档，按字节数和 SHA-256 比对，只把字节变了的文件装进去。留
在机器上的那些写进 bundle 里的 `update/plan.json`，逐个记下路径、字节数和摘要，运行时会先读这份计
划。只有那一版的清单文件在、且每个预期文件都对得上，更新包才往下走；有一个对不上，就在写第一个字
节之前拒绝，让人改用完整安装包。它留在原地的文件仍然属于这次安装，清单文件记着它们，卸载一并收走。
真要写入的文件，如果机器上那份的字节已经完全相同，也不再复制一遍。这个框架自己不做更新器，和 NSIS
一样。它提供的是做出更新包和跑起新安装包的原语。什么时候去问新版本、要不要自动装，由产品自己决定，
所以这里没有「检查更新」这个开关。

**卸载。** 运行时先结束产品进程，再删除记录下来的快捷方式与文件；声明的用户数据，只有用户取消勾选
保留数据时才会删掉。Windows 不允许进程删除自己正在运行的镜像，所以卸载收尾时，卸载程序会把自己复
制成临时目录里的一个清理副本。副本等卸载程序退出后删掉它，再移除已经清空的安装目录，最后让一个很
快就结束的 `cmd` 脚本删掉自己。目录里还留着用户添加的文件时，这个目录就保留。

**运行日志。** 每次安装或卸载都在磁盘上留一份日志。默认放在临时目录下的 `nano-installer` 目录里，
文件名带着安装程序的名字、时刻和这次做的事；静默运行可以用 `--log` 指定文件。写进去的是这台机器、
产品与安装目录，加上运行的每一步和脚本写下的每一行。日志不放在安装目录里，因为失败的全新安装会把
自己创建的目录撤掉，而那正是最需要日志的时候。向导会把这份文件的路径写在它报出的错误下面，静默运行
则写进标准错误。

**自定义步骤。** 项目里放了 `scripts/install.rhai` 或 `scripts/uninstall.rhai`，安装和卸载步骤就
按脚本走，不走内置步骤。脚本引擎编译在 `nano-installer-core` 里，所以每个运行时都带着它。脚本原语
复用与内置流程相同的部署、回滚与清单文件代码，另外设了操作数上限，所以脚本失控也不会把安装挂死。
项目里放了 `scripts/pages.rhai` 时，翻页由它的 `next_page(from)` 决定，
见[脚本接口](/zh-CN/SCRIPT_API/)。

## 安装包外的 MSI

构建还可以把刚做好的安装包再封一层，做成企业分发的那个包。多给一个 `--msi <文件>`，构建器就会在
工程自己的命令处理过安装包之后，把这份安装包封进一个 `.msi`，进包的是机器真正会装的那份镜像。MSI
把安装包本身作为自己的一个流带着，用一条排进安装脚本的动作，以 `--silent --dir "<目录>"` 把安装包
跑起来；卸载时跑的是安装包部署的那个卸载程序。包里其余东西是 Windows Installer 认定「这个产品装过
了」所需要的登记信息。

装在哪个目录由 MSI 决定，它也得知道从哪里卸掉：要求管理员权限的工程把 `INSTALLDIR` 定在
`%ProgramFiles%\<名字>`，其余工程定在 `%LOCALAPPDATA%\Programs\<名字>`，管理员也可以在 `msiexec`
命令行上另指一个目录。MSI 把它真正用的目录写进自己名下的一处注册表值，卸载时再把这个值搜回来，
这样装在调用者指定目录里的产品照样卸得干净。Windows 显示的是产品自己登记的那一条，而 MSI 把自己
那条从列表里藏起来。新版本的 MSI 与旧版本共用同一个升级码，并在装上新产品之前先收掉旧产品，所以
它是升级，而不是并排多出来的第二个产品。同一天再发一版时三段数字没有变，Windows Installer 不允许
它用同一个产品码再装一遍。那一版是另一个产品码，而升级表把「等于当前版本」也算作要收走的旧产品，
所以结果仍是先收掉上一版再装上，而不是并列两份。

这样做有两个前提。被包的安装包必须支持静默运行，也就是 `advanced.silent_mode_support` 与
`advanced.uninstall_mode_support`，因为 MSI 全程不给它窗口；没声明过的工程会被拒绝出包，而不是
拿到一个装不上的包。另外，管理安装（`msiexec /a`）只把包摊开、不跑这些动作，所以它本身不装产品。

## 工具链

`nano-installer-cli` 和 `nano-installer-gui` 都是薄前端，共用 core 里同一套检查与构建 API，而参数
解析和 eframe 界面代码留在 core 之外，所以 GUI 的 egui、eframe、winit 依赖不会进入任何运行时或
安装包。

`install.require_admin` 与 `ui.dpi_aware` 决定清单文件怎么写：安装包靠这份清单向 Windows 申请需要的
权限，也靠它告诉系统窗口自行缩放。Windows 在进程启动之前就会读取清单，所以这两项必须写成资源，
不能做成运行时选项。

缩放声明写在两个元素里：`dpiAware` 给最低支持的版本、Windows 8 和 8.1 读，`dpiAwareness` 给
Windows 10 1607 及以后读，取值 `PerMonitorV2, PerMonitor`，这样每个受支持的 Windows 版本都能用上
它支持的最清晰显示方式。运行时收到 `WM_DPICHANGED` 后，按新显示器的比例重新排版整页，而不是让
系统拉伸一张位图。
