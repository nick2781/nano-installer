# Test cases

This table is the English text of the "what it checks" column of the test report, one row per case.
Where the report finds no English description here it falls back to the Rust doc comment above the
case, and then to the case name.

| Case | What it checks |
| --- | --- |
| `a_border_layer_paints_a_ring_and_leaves_the_center_empty` | A layer with `border-color` paints a ring: the edge is coloured, the middle stays empty. A control with no `border-color` adds no layer. |
| `a_bound_label_shows_its_own_text_beside_the_value_it_reads` | A `Label` bound with `value-source` appends the value it read after its translated sentence, so one layout reads in any language. With no value to show it leaves a placeholder, not an empty line. |
| `a_broken_project_file_is_reported_to_the_user` | A project file that cannot be read is reported instead of crashing the program. People edit these files by hand, so the window has to survive a broken one: the case breaks the JSON, then a layout, and wants the reason in the sidebar and the log, not a panic. |
| `a_browse_button_opens_the_folder_picker_and_leaving_it_changes_nothing` | A button with the `pick_directory` action opens Windows' own folder picker: a window whose class is the shell's `#32770` appears under the process, with the wizard still beneath it. Close that dialog and the wizard is still there, the client area is the same size and the install process is alive, and not one file was written on the way: leaving the dialog is not choosing. |
| `a_build_reads_the_project_from_disk_in_its_worker_thread` | The build rereads the project from disk in its worker thread; the sidebar summary is only the snapshot from the last check. Delete a project file after that snapshot and the build must fail and name it, because the worker thread inspects the directory again instead of trusting the window. |
| `a_built_in_step_clears_a_script_step_text` | A built-in step takes its name from its own locale key, so text a script published does not stay on it. Progress is clamped to 0 to 100 at the same time, so a script cannot push it past the end. |
| `a_built_setup_carries_a_readable_bundle_and_real_resources` | A built setup is three parts: the stub, the bundle data and the Windows resources. The bundle data describes itself at the very end of the file, which is how the runtime finds it. |
| `a_built_setup_installs_its_payload_and_registers_an_uninstall_entry` | What a setup is for: the payload lands on disk; the manifest records what was written; the uninstall entry is registered in the registry; and the payload's bytes arrive unchanged. |
| `a_bundle_does_not_carry_an_icon_the_build_injects_as_a_resource` | An icon the build injects into the executable as a PE resource does not also travel in the bundle, because nothing there opens it. |
| `a_button_state_image_falls_back_to_the_normal_one` | A layout that draws only some states still draws its buttons: a missing `hover-image`, `pressed-image` or `disabled-image` falls back to `normal-image`. A button held back by a condition prefers `disabled-image`, and a control with no id gets neither hover nor press. |
| `a_button_waits_for_each_state_its_condition_can_name` | `enabled-when` makes one control depend on another. The four states the guide lists, `checked`, `unchecked`, `visible` and `hidden`, are judged by the check box or panel they name. Written as comma-separated conditions it holds only if all of them hold, and an empty condition left by a spare comma counts as not holding. A state the runtime does not understand and a control the page does not contain both hold the button back instead of letting the click through. A button with no condition is enabled, so the attribute is optional. |
| `a_button_waits_for_the_field_its_condition_names` | When `enabled-when` names a text box, the button waits for that value to be valid. While the field is empty (which is what `required` describes) the install button registers neither a click region nor hover; a path the project accepts gives the click back, and clearing it takes the click away again. The button on the same page that writes `dir:invalid` does the opposite. |
| `a_byte_order_mark_on_a_project_json_file_is_taken_off` | An `installer_config.json` or `locales/*.json` that starts with a UTF-8 byte order mark reads fine. Windows editors write the mark, and the parse used to fail on it. It is taken off on the way in and never reaches the copy the runtime parses out of the bundle. A layout XML was never affected. |
| `a_call_is_two_names_and_a_path_is_not_one` | The first argument of `plugin_call` has only one form, `dll::function`: one with both parts is accepted. One missing a part, one with only one part, or one written as a path (with a separator or `..`) is refused on the spot. A plugin is recognised by the DLL name the project carries in the package, not by a path. |
| `a_caret_sits_after_the_characters_before_it` | The text caret is drawn after the characters before it, and moves right with the index. Past the length of the text it stays inside the text box. |
| `a_cancel_button_stops_the_project_script_and_leaves_nothing_installed` | A page puts out a button with `action="cancel"`, and the case clicks it in a real window: the running task stops at the script step, the wizard returns to the page the task started on, the directories the script had created are taken back, and not a byte is left behind. |
| `a_cancel_request_stops_the_checkpoints_that_follow_it` | A checkpoint that receives a cancel request reports `cancelled by the user` under its own error type, so the wizard says the run was cancelled rather than failed. The cancellation applies to this one task; the next task gets a fresh handle. |
| `a_cancelled_deployment_writes_nothing` | When a deployment is already asked to cancel at the start, not one file is copied. The rollback then deletes the whole install directory this run created. |
| `a_cancelled_install_gives_up_after_the_script_and_undoes_what_it_wrote` | The script notices the cancellation itself, ends the long step and returns normally. The runtime then stops at the checkpoint after the script, reports `cancelled by the user`, and the directories the script wrote are taken back with it. |
| `a_changed_or_new_file_travels_in_the_update` | A file whose contents changed, and a file that only this version has, both travel in the update package: not one more, not one fewer. |
| `a_client_reading_the_page_does_not_take_the_wizard_down` | Editing a text box while a client is attached does not take the wizard down: the client reads the page, the user fills the text box in and clears it, the client reads it again, and the process is still alive. This case guards a real crash: an empty text box that was cleared draws a run of text with no characters, and the dangling pointer of the empty buffer makes `user32`'s `DrawTextW` fault (`0xc000041d`). |
| `a_click_on_a_radio_is_the_value_the_install_waits_for` | Clicking a radio button in a real window: the install button waits for the value of the row that was clicked. Clicking install first does nothing; clicking the row the layout selects by default and then install still does nothing; clicking another row and then install switches the window to the task page and installs the product into the configured directory. A layout-level case only proves a click becomes an action; this one proves the window records which row was clicked. |
| `a_client_names_a_child_with_what_it_is_told_to` | A client names a control by number and names the window itself with an empty variant; each reads as what it means. Naming an "object child" is refused rather than answered with another control: the wizard's controls are all simple children, so there is no object child to give. |
| `a_control_is_named_by_what_it_declares_when_it_draws_no_words` | A control that draws no words can still be named for a screen reader: `accessible-name` as an `@key` is looked up in the current language, plain text is used as written, and it wins over `text` when both are declared. Link markup inside drawn words is not read out: the client gets the sentence with the markup removed. |
| `a_control_is_reported_as_what_a_screen_reader_calls_it` | Each control type the layout records maps to a role in `oleacc.h`: button, link, check box, radio button, combo box, text box. Those are the ones a client has to read; the wrong one makes what is announced wrong. |
| `a_closed_language_select_draws_its_arrow_over_its_fill_and_outline` | A collapsed `Select` is three layers: the fill, the outline and the arrow. The arrow is inset from the far edge, centred vertically, and grows with the display scale. Collapsed it draws the downward one; expanded, the upward one. |
| `a_component_project_is_refused_an_update_package` | A project split into components cannot make an update package: there is no archive to compare against. The build refuses on the spot and tells you to ship a full setup as before, and after the refusal not one setup file is left behind. |
| `a_configured_percent_path_is_expanded_and_used` | A configured path with `%LOCALAPPDATA%` has to be expanded before it is used. An unexpanded path is not absolute, and the install refuses a relative directory. This case runs with no `--dir` at all, the same as a silent run that names no directory. |
| `a_container_measures_the_edge_its_children_are_asked_for` | Asking an `HBox` for its vertical size reports the tallest child plus its own top and bottom padding; asking for the horizontal direction reports the sum of what the children ask for along the width. A nested percentage-width container measures through its own children, so it neither stretches the outer row nor collapses it. |
| `a_control_names_the_colour_of_its_own_focus_ring` | The focus ring's colour is the control's own to name: `focus-color` on the control wins, otherwise the page's, and only when neither writes one does the default accent colour apply. The case reads the painted pixel back and checks it. |
| `a_control_the_page_keeps_out_of_reach_is_not_in_the_tab_order` | A control the page holds back does not enter the Tab order: a button held back by `enabled="false"` or by a condition, a `readonly` text box, an element with `visible="false"` and a label that declares no `action` all get no keyboard. A text box with no `id` cannot enter either, because the keyboard has no name to record when it lands there. |
| `a_directory_a_script_created_is_kept_while_it_holds_a_user_file` | A directory the project's script created is left where it is when the uninstall finds something in it that the installation never put there, and nothing inside it is touched. |
| `a_directory_a_script_created_is_removed_with_the_installation` | A directory the project's script created with `create_dir` is recorded in the manifest, so the uninstall removes it once it is empty; a setup carrying no `directories` field behaves as it did before and removes none. |
| `a_directory_an_earlier_install_created_is_removed_after_an_upgrade` | An upgrade carries over the directories the earlier install recorded and that are still on disk, so uninstalling after an upgrade removes them too, while an entry that is no longer a directory is dropped rather than kept. |
| `a_disabled_control_is_described_as_unavailable_even_though_the_keyboard_skips_it` | A control the page cannot use yet stays in the accessibility tree at the place the layout puts it, named and carrying the unavailable state, while the Tab ring still skips it and its default action is refused. |
| `a_damaged_bundle_entry_is_refused_and_leaves_no_copy` | Every entry in the bundle index records the digest computed at build time, and reading it checks that: a payload changed by one byte is reported by name, stating the recorded value and the actual digest. An untouched entry in the same package still reads. Streaming a damaged entry reports an error and leaves no copy on disk, so the step that would decompress it has nothing to start from. |
| `a_default_log_is_named_after_the_image_the_moment_and_the_task` | When no log file is named, a run writes its log into the `nano-installer` directory under the temporary directory. The file name carries the installer image's own name, the moment, and what this run is doing (install or uninstall). The same setup run on two machines at two moments gives support a name that tells them apart, and the two runs do not overwrite each other. |
| `a_dependency_that_cannot_be_installed_stops_the_install` | A required dependency that cannot be installed stops the install, and stops it before the product lands on disk. The error names the dependency and the exit code the installer returned (the command in this case returns 7), and the destination directory does not exist afterwards. When the machine cannot give the product what it needs, you see this message instead of a product that will not start. |
| `a_dependency_the_machine_already_has_is_not_installed_again` | When the machine already has what the product needs, it is not installed again: the rule recognises it, so the installer does not run once. The case writes the installer's arguments as a command bound to report an error and marks the dependency required, so an install that really ran would fail on the spot instead of quietly passing. |
| `a_dialog_button_answers_with_its_own_action` | A button in a dialog registers a click region from the action it declares: the confirm key gives `DialogOk`, the cancel key gives `DialogCancel`. |
| `a_dialog_button_is_drawn_from_the_question_rather_than_the_layout` | One dialog layout serves every question. The words on the buttons come from the dialog state itself, the three roles of question, confirm and cancel. A role the dialog gives no text for shows no content, and the layout's hard-coded placeholder does not come up in its place. |
| `a_dialog_covers_the_page_without_a_focus_ring_behind_it` | While a dialog is open the page is still drawn beneath it, but no focus ring: this stretch of keyboard belongs to the dialog, and a ring on the page would point where pressing does nothing. Compare the layers before and after it opens, and the missing one is the ring. |
| `a_dialog_is_drawn_over_the_page_and_centred` | A dialog is drawn over the page and centred when it is smaller, so its own layout can use ordinary coordinates. The question text comes from the dialog, not from the layout's placeholder. |
| `a_directory_written_with_a_trailing_dot_component_is_the_directory_itself` | When a package hands over a directory it writes `"<目录>\."` (a directory attribute formats with a trailing backslash, and a backslash before a quote is an escaped quote in command-line parsing). That path and the one without the dot mean the same directory, and the run records the one without the dot. A path that is only whitespace is refused as before. |
| `a_disabled_button_registers_no_click_and_no_hover` | While the condition does not hold the button is inert: no click region, no hover region. Once it holds, the button goes back to its declared action, and the region is the rectangle the layout gives it. |
| `a_display_scales_the_layout_by_its_own_dpi` | With DPI awareness on, 96 DPI is 1.0, 144 and 192 DPI are 1.5 and 2.0, and 120 DPI is 1.25 but still takes the 1x assets. With it off, a project stays at the 96 DPI baseline on whatever monitor it lands on, and the shell does the scaling. |
| `a_double_click_selects_the_word_under_the_pointer` | A double click selects the word under the pointer: letters and digits join into one run, a path separator is a run of its own, whitespace counts as one run, and an underscore counts as part of a word. A click outside the text has nothing to select. |
| `a_download_that_is_not_the_recorded_file_is_refused` | When the download is not the file the project recorded, not one byte runs. The URL answers with a real executable, the digest has the right number of digits but is not its: the download fails on the spot, says what arrived and what was expected, and leaves neither the target file nor the installation directory. This is how a tampered or truncated release is kept out. |
| `a_downloaded_dependency_is_checked_before_it_runs` | A dependency the setup cannot carry is fetched at install time: a server is opened on the machine's loopback, a real executable comes back, the hash has to match before it is let through, and only then does it run and leave what it should. The check uses a digest computed by the certutil that ships with Windows, not one the runtime computes for itself. |
| `a_failed_upgrade_restores_the_previous_version` | An upgrade that fails midway (the registry registration is made to fail here) rolls back to the previous version: the old files and the old manifest are restored, no file of the new payload is left, and the manifest holds only the old files. |
| `a_failing_install_script_removes_what_it_wrote` | When an install script throws, what it wrote is cleared away, the error carries the message the script threw, and the install directory keeps no leftovers. |
| `a_failing_run_leaves_its_log_behind_and_names_it` | A failed run leaves its log for the user and writes its full path to standard error. When a script throws, the log holds the product name, the line the script wrote before it failed, and the error with its original message, while the product leaves not one file behind. A failed install takes away what it created, and the log is not in that directory, so it is still there after that. |
| `a_failure_notice_points_at_the_log_of_the_run` | When the wizard reports a failure it names the log file this run wrote, on top of the error itself: that line is the one thing you can hand on. With no log to point at (before a window is even created, say) the notice does not mention one, and neither does a successful install. |
| `a_field_checks_the_value_the_project_asks_it_to` | A field's own rules are written in the layout: `required` covers whether a value is there; `min-length` and `max-length` count characters (a Chinese character counts as one, not by bytes); `pattern` is a mask rather than a regular expression, `*` is a run of any length (it may be empty), `?` is exactly one character, and the whole value has to fit. So an installation directory written `?:*` asks for a path that starts with a drive letter. A field with no rule is valid, and a field that may be left empty is valid while it is empty. The first rule the value breaks leaves its own message; a rule with no message only makes the field invalid and says nothing. |
| `a_field_the_user_fills_in_is_what_lets_the_install_start` | The whole path a project asks you to walk, in a real window: with the field empty a click on install does nothing, and ticking the agreement alone does not do it either; only after a path is typed in character by character does the install start, with the product landing in the directory you typed. If any of the three links is not joined up -- the field, the button's condition, the install action -- it stops where it is. |
| `a_file_that_is_not_an_image_is_refused` | At build time, a text file in the plugins directory that has only had its extension changed is refused by name. The build does not wait for install time, when `LoadLibrary` would answer "is not a valid Win32 application" and the author would not know which half to change. |
| `a_file_that_moved_in_size_travels` | A file whose size moved still travels with an update package: the size is looked at before the digest, so a changed size does not count as unchanged even when the digest is the same. |
| `a_file_type_that_would_write_outside_the_classes_tree_is_refused` | Both names of a file type are checked before they are used: a path separator in the extension or the program id, or either of them empty, makes the call return `false` at once. A call with an empty command line is refused too, because such a file type opens nothing. Five refused calls wrote not one byte into the registry, and the manifest records none of them. |
| `a_finalize_command_runs_on_the_finished_setup_and_uninstaller` | The project's own command runs on the finished files. The uninstaller is processed once while it is still a file of its own and not yet embedded, so the mark lands on that entry inside the setup. It is processed again once the setup and its footer are written, so the mark lands at the end of the file, where a signature will grow. The two commands each get their own file (the uninstaller first, the setup second), and the setup that was processed installs as usual and registers its uninstall entry. |
| `a_finalize_command_runs_on_the_package_a_build_writes` | When the build asks for `--msi`, the project's own command gets the enterprise package too: it is handed the `.msi` itself (the case records the path the command received). And the size the build reports is measured from disk after the command has run, since signing rewrites the file, so a wrong size means the package that went out and the record disagree. |
| `a_finalize_command_that_fails_stops_the_build` | A command that refuses the file stops the build: the error names the setting and the exit code the command returned, and the line the command wrote goes into the build log too. The setup that was not signed does not stay on disk. |
| `a_finalize_command_that_refuses_the_package_stops_the_build` | A command that refuses this `.msi` stops the build, and the package is not left on disk, so the next pipeline step cannot pick up a package nobody signed. |
| `a_hidden_element_takes_its_whole_subtree_with_it` | `visible="false"` on an ancestor hides the whole subtree beneath it: a child control's action, its words and the panel's own background are not painted, and nothing else on the page is affected. Set the attribute back to `true` and the branch is painted in full again. |
| `a_high_contrast_machine_gets_the_colours_the_scheme_keeps` | A real window is run once with each answer. The fixture declares the machine's own colours swapped (the page background is written as `COLOR_WINDOWTEXT`, the focus ring as `COLOR_WINDOW`, the card's fill and outline as `COLOR_HIGHLIGHT`). With the setting off, what is read back is exactly those declared colours, and the checkbox's picture is unchanged in both cases. With it on, the page background, the card and the card's edge become the machine's `COLOR_WINDOW`, `COLOR_BTNFACE` and `COLOR_WINDOWFRAME`, and after one Tab the ring becomes `COLOR_HIGHLIGHT` rather than the declared colour. Finally a `WM_SETTINGCHANGE` is sent to the window and the two frames are compared pixel by pixel: the window did not move by one pixel, and is still there. The switch belongs to the user, so the case only writes the answer into the process and does not touch this machine's settings. |
| `a_hint_shows_the_rule_the_value_breaks` | A label bound to `value-source="field-error:<字段 id>"` draws the message the broken rule wrote: with the field empty it reports the `required` message, with a value that is not valid the `pattern` message, and the message is looked up in the project's own language. While the value is valid the label draws nothing, and so does one that names a field the page does not have. |
| `a_hook_must_answer_with_page_text` | A page hook's `next_page` has to answer with text: a boolean, a number or the like is refused on the spot with a word on what to return, instead of being read as the name of a page. |
| `a_hook_names_the_page_the_wizard_goes_to` | A page hook decides the next page from `from`: naming one page goes there, and an empty answer hands the order back to the page order the project declares. A page the hook does not mention follows the declared order as well. |
| `a_hook_reads_the_wizard_and_the_machine` | What a hook reads is the value the wizard holds right now and the answer the machine gives right now: `get_mode()` says whether this run is an install or an uninstall, `get_install_path()` and `file_exists` ask about the same directory, and the answer follows the value passed in rather than being a hard-coded constant. |
| `a_hook_that_fails_reports_the_project_message` | A hook that throws reports `scripts/pages.rhai failed:`. The lines the project wrote itself with `log_error` come back to the caller with the error, the same as when a task script fails. |
| `a_hover_and_a_press_show_the_pictures_the_button_declares` | The pointer is driven in a real window: when it lands on the button the window paints `hover-image`; held down, it paints `pressed-image`; when the pointer leaves the window the button goes back to `normal-image`, and the whole frame is not one pixel different from before the pointer came. Each of the three state images and the page background is one flat colour, so reading the single point at the button's centre says which one is up; and looking at whether the change landed outside the button's rectangle says what changed is the button, not the whole page painted again. |
| `a_label_takes_its_text_font_and_alignment_from_the_layout` | A `Label`'s content is all text: its font size, bold, colour and alignment take effect as the layout writes them, and `value` is accepted the same as `text`. A label with no alignment starts at its own left edge, and its font size follows the display scale too. |
| `a_language_menu_lists_its_options_and_marks_the_one_in_use` | An open language menu paints above the page, one row per option; the row of the language in use is filled with the selection background; options with `visible="false"` do not appear. Clicking a row gives the region that switches to that language. |
| `a_layout_picks_the_image_density_the_display_asks_for` | The layout names one file name, and the runtime picks the version: a low-density display uses 1x, a high-density one uses `@2x`. A file name written as `@2x` outright is normalized as well, and when only one of the two ships it falls back to the other. |
| `a_link_the_project_does_not_configure_stays_plain_text` | The last item in the guide's order of resolution: a link whose target does not resolve stays plain text. The words show as usual, a click does nothing, and the label does not fail to draw because of it. |
| `a_latin_code_page_cannot_hold_a_chinese_name` | A Latin code page can never hold a Chinese name. The build-time check rests on that fact, and it does not depend on what is installed on the machine. |
| `a_plugin_answers_the_script_that_calls_it` | A setup that ships a plugin is really installed once: `sample::About` gets the plugin's version string; `sample::Add` adds its arguments up to 42 (arriving in the order the script wrote); `plugin_values` takes back the three values `Echo` pushed back; the installation directory `Where` names is the directory this run installed into; `Note` succeeds as usual after writing two lines into the log; and `RequiresAbi` gives `abi 1` while the host ABI is new enough. Text in, text out, with nothing left to a guess. |
| `a_plugin_that_fails_is_reported_to_the_script` | Each of the two reportable ways third-party code can fail is walked once: a plugin explains itself and then returns a failure code, and a plugin refuses an ABI it does not know. The script catches both with `try`, and the error carries the plugin's file name, the function name and the return code. Two more failures belong to the call itself (the DLL has no such export, the setup does not ship that plugin at all), and each of those has its own word too. A plugin that panics is not in this case: Rust aborts the process outright when a panic would cross the `extern "system"` boundary, and the host has no time to report it, which is written into `nano_plugin.h`. |
| `a_plugin_that_is_not_an_image_is_refused` | A file in the plugins directory that is not an image is refused by name at build time too, and the reason has to carry the file name. |
| `a_plugins_writes_are_taken_back_by_the_uninstall` | What a plugin writes through the host travels with the uninstall: the `plugin-sample.txt` it writes into the installation directory and the registry value it writes can both be read after the install; after the uninstall neither is there. In the same run it tries to write a file outside the installation directory: the host refuses on the spot and hands the reason back to the plugin. "A plugin writes only where the uninstall takes it back" does not rest on the author's good behaviour. |
| `a_plugin_written_in_c_is_called_the_same_way` | The ABI is the header's business, not one language's. The setup this case installs ships a plugin written in C (compiled from `examples/plugin-c/sample.c` by MSVC alone, with no Rust toolchain involved): it answers values, reports the installation directory and the argument count through the services, writes a file and a registry value through the host (the uninstall takes both back), and fails with its own return code. The uninstall script calls it once too, and that is another run of another image, since the uninstaller carries its own bundle, so this case says at the same time that a plugin travels in that one as well. A second implementation is the evidence for the sentence "the structure and the calling convention belong to the header, not to one compiler". |
| `a_product_name_is_stored_whole_or_the_build_is_refused` | The tables in a package are stored in the build machine's ANSI code page (measured to be so, and declaring a code page does not change it), so the product name is either stored as it is or this build is refused: storing it as a run of replacement characters is never allowed. The case asks for what this machine can do: if the name can be stored it has to read back unchanged; if it cannot, the build has to fail and point out the code page the machine uses. |
| `a_name_too_long_for_a_short_name_carries_one_the_file_system_can_keep` | When the product name is too long or is not Latin letters, the installation directory is declared as "short name\|long name": the short name is generated from the ASCII letters and digits in the name, the two-character tag takes the digits in the name (the digest when there are none), and the product name follows the bar as it is. The names Windows keeps for devices (`CON` and the like) get a short name too; one name gets the same short name every time. |
| `a_nested_container_reports_the_extent_its_children_need` | A panel with no declared size is as big as its content: along its own axis the children and the gaps are added up, across the axis the largest child is taken, and its own padding counts once.
