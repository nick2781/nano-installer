# 配置与脚本边界

`nano-installer` 的设计原则是：

- 配置描述安装器的通用能力
- 布局描述界面结构和默认交互
- 脚本表达产品业务逻辑和副作用

这样做的目标是把“框架能力”和“产品差异”拆开，避免把某个业务项目的特殊需求固化进 runtime。

## 什么适合放在配置里

配置适合表达稳定、可复用、跨产品都成立的能力，例如：

- 安装路径和空间要求
- 快捷方式能力
- 开机自启能力
- 通用注册表项
- 多语言和资源目录
- 窗口尺寸、DPI 阈值
- 页面流程定义
- 静默安装、更新、卸载模式支持

这些能力的共同点是：

- 不依赖某个具体产品的业务语义
- 可以被不同项目重复复用
- 安装器 runtime 可以稳定抽象

## 什么适合放在布局里

布局适合表达页面上的结构和默认状态，例如：

- 哪个页面显示哪些控件
- 某个复选框是否显示
- 某个复选框默认是否勾选
- 控件间距、位置、图标、字体、图片
- 对话框尺寸和页面排版

典型例子：

- 是否显示“保留数据”选项
- “保留数据”默认是否勾选
- 自定义安装区域展开还是收起

这些都属于 UI 语义，不应该继续塞回 `installer_config.json`。

## 什么适合放在脚本里

脚本适合表达产品业务副作用，也就是“安装器框架本身无法通用抽象”的部分，例如：

- 写入 `channel.conf`
- 写入渠道标记文件
- 删除产品自定义目录
- 删除产品自定义注册表键
- 注册 URI Scheme
- 卸载时保留或删除某些业务数据
- 其他安装后或卸载时的产品定制动作

这些动作通常会随着业务变化而变化，不应该成为 runtime 的固定字段。

## 一个简单判断标准

可以用这个问题来判断：

> 这个能力是否能被另一个完全不同的产品，几乎不改语义地直接复用？

如果答案是：

- `能`：优先考虑配置
- `更像界面默认状态`：优先考虑布局
- `不能，而且明显带业务语义`：优先考虑脚本

## 示例

适合配置：

- `shortcuts.desktop_shortcut`
- `autostart.enabled`
- `registry.uninstall_key`
- `advanced.silent_mode_support`

适合布局：

- `chkReserveData` 是否出现
- `chkReserveData checked="true"`
- `langSelect` 的尺寸和图标
- 安装中页进度条图片

适合脚本：

- 生成 `channel.conf`
- 删除渠道缓存目录
- 删除某个产品私有注册表键
- 根据 `keep_data` 决定是否保留数据目录

## 推荐实践

- 先问“这是通用能力，还是产品逻辑”
- 能用配置表达的，不要先写脚本
- 不能稳定抽象的，不要硬塞进 runtime
- UI 默认状态优先放在 XML，而不是 `installer_config.json`

这条边界保持清晰，安装器才能长期对外发布而不被某个业务项目拖偏。
