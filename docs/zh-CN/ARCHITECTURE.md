# 架构

## 从一个项目目录到单个可执行文件

```text
MyApp/
  installer_config.json + layouts/ + assets/ + locales/ + scripts/ + payload/
                                    |
                                    v
                     nano-installer-native-x64.exe
                                    |
                        按 payload 文件头选择运行时
                            /                       \
                lzma-stub-native.exe        zlib-stub-native.exe
                            \                       /
                            + bundle + 卸载程序
                                    |
                                    v
                             MyApp_Setup.exe
```

构建器与运行时是两个独立的程序。生成的安装包只包含运行时和你的项目数据，永远不含构建器。

构建器先看 payload 的头几个字节：`7z` 签名走 LZMA 运行时，`PK` 签名走 ZIP 运行时。接着它复制
对应的运行时，写入你配置的图标、版本信息和应用程序清单，再追加一份 bundle，里面装着 layouts、
assets、locales、scripts 与 payload，最后是自包含的卸载程序。payload 保持你给的压缩格式，
打包时不会再压一层。

写完安装包之后，构建器还会把两个成品交给工程自己的命令再走一步：卸载程序在还是独立文件的时候、
被嵌进去之前跑一次，安装包在全部写完、文件关掉之后跑一次。命令写下的每一行都进构建日志，返回非零
就中止构建，那份被拒的安装包也不会留在磁盘上。签名是这两个钩子（NSIS 的 `!finalize` 与
`!uninstfinalize`）通常的用途，构建器自己不签名，配法见[配置参考](CONFIG_REFERENCE.md#构建完成后的命令)。

## 生成的安装包内部

**启动。** bundle 的尾部有一份索引，运行时靠它找到每个条目，条目旁边记着构建时算出的 SHA-256，
所以启动时不用把 payload 载入内存，读出来的字节也一定是当时写进去的那些；真正开始解压时才按偏移
读取，边读边核对摘要，对不上就按条目名报错、把写了一半的那份删掉。

**界面。** 页面取自 `wizard.pages`（安装）和 `wizard.uninstall_pages`（卸载）。每个页面都用
Win32 绘制，PNG 交给 WIC 解码，透明通道用 GDI alpha blend 合成。目前支持：绝对定位的位图与文字
层，可嵌套的 `VBox`/`HBox`/`Content` 流式布局（内边距、外边距、百分比尺寸、`flex-wrap` 折行都
在内），进度条，复选框与可展开面板交互，可点击链接，就地文本编辑（选区、剪贴板与撤销栈），目录
选择框，运行时切换语言，没有边框、四角是圆的窗口，任务栏图标，双缓冲绘制，拖动、最小化和关闭。
页面用 `action="next"` 与 `action="back"` 前后走；项目里放了 `scripts/pages.rhai` 时，每次点
`next` 先问它的 `next_page(from)` 去哪一页，钩子拿到的只有只读原语，`back` 则按用户来时的路
退回来。

**读屏。** 运行时把控件都画成像素，窗口里没有子窗口给客户程序去走，所以窗口自己回答 Windows 问的
那句「你在显示什么」：收到 `WM_GETOBJECT` 时用 `LresultFromObject` 交出一个 `IAccessible`，由 COM
封送到客户程序所在的进程里去。报出去的是这一页按版面顺序排开的控件——角色、名字（版面写下的文字；
输入框取它上方的标签，下拉框取它当前显示的那一行）、取值、状态与屏幕坐标，客户程序请求执行默认动作
时走的就是用户点一下的那条路。焦点移动、取值与清单变化、翻页都由窗口主动发通知，对话框打开时整棵树
换成卡片上的两个答案、窗口的名字换成那句提问。**任务正在跑的时候**没有控件可点，剩下的就是任务自己
报的那句话和一根进度条：这两样按「被描述的对象」一起报出去（进度条的取值是它画着的百分比），并且每
变一次都由窗口主动播报——状态文字按活动区域播报，进度条报成取值变化，两样都只在真的变了才报一次。输入框破坏规矩时那句提示同样在这里：它既是这个字段自己的描述，也在出现或换一条规矩时按活动区域播报。窗口打开的**那一帧只记不报**：那是阅读器自己会读到的内容，一个用户可以在第一帧画出来之前就开始打字，所以基准值是建窗口时记下的，不是第一次重画时记下的。
实现都在 `crates/nano-installer-core/src/accessibility.rs`，清单每次都从运行时那份共享状态现算，
没有第二张要与页面对齐的表。

**提问与提示。** 要用户回答的问题（如退出确认）和要用户看到的提示，都画在窗口内部，用的是
`ui.dialog_layout` 指定的那份布局，不交给系统弹窗。对话框就是一份普通布局，
`value-source="dialog:*"` 让它显示这次提问的正文和按钮文案；打开期间只有对话框上的控件响应点击，
`Enter`/`Escape` 分别对应确认和取消。脚本的 `show_message`、`show_error`、`ask_yes_no` 也画在
这张卡片上，被点中的那个按钮就是交还给脚本的答案。窗口按所在显示器的工作区居中，布局比桌面还大
时夹取到工作区内。

**任务。** 安装和卸载都在工作线程上跑，进度与页面切换靠一份共享状态发布出去；UI 线程收到刷新消息
后重绘。绘制始终留在持有窗口的那个线程上，所以解压期间窗口照样能响应。

**安装。** 文件先暂存，然后写入 manifest 和卸载注册表，再创建配置的快捷方式与自启动项。卸载
注册表写的是 Windows 安装列表要的整组字段：产品名、版本、发布者、安装目录、卸载命令与图标，
静默卸载命令，按磁盘字节数算出的容量，以及两个声明这里没有修改与修复步骤的标记。目标目录
里已有同一项目时按升级处理：被替换的文件记入回滚日志，新版 payload 里已经没有的文件会删掉，
失败就恢复到先前版本。

**更新包。** 一次发布可以做成更新包而不是完整安装包：`--delta-from` 点名它要替代的那一版的 payload
归档，构建器用运行时分别展开两份归档，按字节数和 SHA-256 比对，只把字节变了的文件装进去；留在机器
上的那些写进 bundle 里的 `update/plan.json`，逐个记下路径、字节数和摘要。运行时会先读这份计划：
只有那一版的 manifest 在、且每个预期文件都对得上，更新包才往下走；有一个对不上，就在写第一个字节
之前拒绝，让人改用完整安装包。它留在原地的文件仍然属于这次安装——manifest 记着它们，卸载一并收走；
真要写入的文件，如果机器上那份的字节已经完全相同，也不再复制一遍。
这个框架自己不做更新器，和 NSIS 一样：它提供的是做出更新包和跑起新安装包的原语，什么时候
去问新版本、要不要自动装，由产品自己决定，所以这里没有「检查更新」这个开关。

**卸载。** 先结束产品进程，再删除记录下来的快捷方式与文件；声明的用户数据，只有用户取消勾选保留
数据时才会删掉。Windows 不允许进程删除自己正在运行的镜像，所以卸载收尾时，卸载程序会把自己复制成
临时目录里的一个清理副本：副本等卸载程序退出后删掉它，再移除已经清空的安装目录，最后让一个很快
就结束的 `cmd` 脚本删掉自己。目录里还留着用户文件时就保留。

**运行日志。** 每次安装或卸载都在磁盘上留一份日志，默认落在临时目录下的 `nano-installer` 目录
里，文件名带着安装程序的名字、时刻和这次做的事，无窗口运行可以用 `--log` 指定文件。写进去的是这
台机器、产品与安装目录，加上运行自己的每一步和脚本写下的每一行。日志不放在安装目录里：失败的
全新安装会把自己创建的目录撤掉，而那正是最需要日志的时候。向导把这份文件的路径写在错误下面，
无窗口运行写进标准错误。

**自定义步骤。** 项目里放了 `scripts/install.rhai` 或 `scripts/uninstall.rhai`，安装和卸载步骤就
按脚本走。脚本引擎编译在 `nano-installer-core` 里，所以每个运行时都带着它；脚本原语复用与内置流程
相同的部署、回滚与 manifest 代码，另外设了操作数上限，脚本失控也不会把安装挂死。项目里放了
`scripts/pages.rhai` 时，翻页由它的 `next_page(from)` 决定，见[脚本接口](SCRIPT_API.md)。

## 安装包外的 MSI

构建也可以把刚做好的安装包再封一层，做成企业分发的那个包：多给一个 `--msi <文件>`，构建器就在
工程自己的命令处理过安装包之后，把这份安装包封进一个 `.msi`——进包的是机器真正会装的那份镜像。
MSI 把安装包本身作为自己的一个流带着，并用一条排进安装脚本的动作以
`--silent --dir "<目录>"` 把它跑起来；卸载时跑的是安装包部署的那个卸载程序。包里其余东西是
Windows Installer 认定「这个产品装过了」所需要的登记信息。

装在哪个目录由 MSI 决定，因为它也得知道该从哪里卸：要求管理员权限的工程把 `INSTALLDIR` 定在
`%ProgramFiles%\<名字>`，其余工程定在 `%LOCALAPPDATA%\Programs\<名字>`，管理员可以在
`msiexec` 命令行上另指一个目录。MSI 把它真正用的目录写进自己名下的一处注册表值，卸载时再把这个值
搜回来，因此装在调用者指定目录里的产品照样卸得干净。Windows 显示的是产品自己登记的那一条，MSI 把
自己那条从列表里藏起来。新版本的 MSI 与旧版本共用同一个升级码，并在装上新产品之前先收掉旧产品——
所以它是升级，而不是并排多出来的第二个产品。同一天再发一版时三段数字没有变，Windows Installer
因此不允许它用同一个产品码再装一遍；那一版是另一个产品码，而升级表把「等于当前版本」也算作要收
走的旧产品，所以结果仍是先收掉上一版再装上，而不是并列两份。

随之而来有两个前提。被包的安装包必须支持无窗口运行（`advanced.silent_mode_support` 与
`advanced.uninstall_mode_support`），因为 MSI 全程不给它窗口：没声明过的工程会被拒绝出包，而不是
拿到一个装不上的包。另外，管理安装（`msiexec /a`）只把包摊开、不跑这些动作，所以它本身不装产品。

## 工具链

`nano-installer-cli` 和 `nano-installer-gui` 都是薄前端，共用 core 里同一套检查与构建 API。参数解析
和 eframe 界面代码留在 core 之外，所以 GUI 的 egui、eframe、winit 依赖不会进入任何运行时或安装包。

`install.require_admin` 与 `ui.dpi_aware` 决定清单怎么写：安装包靠这份清单向 Windows 申请需要的
权限，也靠它告诉系统窗口自行缩放。Windows 在进程启动之前就会读取清单，所以这两项必须写成资源，
不能做成运行时选项。

缩放声明写在两个元素里：`dpiAware` 给 Windows 7/8/8.1 读，`dpiAwareness` 给 Windows 10 1607 及
以后读，后者取值 `PerMonitorV2, PerMonitor`，这样每个受支持的 Windows 版本都能用上它支持的最清晰
显示方式。运行时收到 `WM_DPICHANGED` 后按新显示器的比例重新排版整页，而不是让系统拉伸一张位图。
